## Reader guide

The central question is **what the study assessed, at which unit, and against which criteria**. Read the source reports and supplement in this order.

1. Use `primary_unit` and `required_related_ids` to identify the study, report, dataset, outcome, model, development or evaluation unit and its links.
2. Check `Applicability`, then apply `Question/item`, `Allowed responses` and `Decision and exceptions` together.
3. Separate numeric/free-text values from status. Enter values only for `REPORTED`; use `NR` for nonreporting, `NA` for structural inapplicability, and `UNCLEAR` for conflicting or insufficient evidence.
4. Link judgements to source/supplement pages or objects and start/end anchors. Do not collapse repeated outcome, model, development or evaluation units into a study-level response.
5. Detailed records are authoritative. Derive manuscript/figure summaries and denominator flags from them rather than entering summaries again.

The public materials have distinct roles.

- **Canonical protocol §15**: all 17 metadata fields and decision rules for 382 items.
- **Supplementary Table S2**: a seven-column human-readable instrument with units, links, applicability, choices, individual rules and evidence requirements.
- **Supplementary Table S5**: an eight-column dictionary for the 158 S7 `STUDIES` variables in matching order.
- **Supplementary Table S7**: study values and repeated units; `DATA_DICTIONARY` and `PROTOCOL_CROSSWALK` retain full technical metadata and traceability.

File and verification-layer descriptions below document reproducibility and internal management. The manuscript and readable S2 use the content criteria and variable definitions above.

### Eligibility decision key (ELG02, ELG05–07)

This is the applied policy in the current manuscript Methods and screening ledger, not a new inclusion rule. Apply the following conditions together.

| Decision | Operational boundary and example |
|---|---|
| Eligible analysis | KNHANES is actually analysed and eligible ML is central to the primary objective. Eligible families include tree ensembles, boosting, support vector machines, k-nearest neighbours, naive Bayes, neural networks/deep learning, automated ML and large language models. |
| Adjacent-only analysis | Classical clustering, PCA/factor analysis, latent class/profile, penalised regression or association rules without a central eligible ML component are catalogued as ML-adjacent. A clustering task can qualify when an eligible neural representation is central; classical clustering alone does not. |
| Analytic role | PCA as preprocessing before a central eligible neural model does not alone exclude the report or determine its task. An ancillary eligible-model comparison does not make an adjacent-only primary objective eligible. |
| Complete report | Recoverable analytic methods and results must establish the eligible analysis. Format, identifier, language or publication venue alone do not decide eligibility; isolated abstracts, protocols and reviews without an eligible original analysis are excluded. |
| Linkage and KNHANES role | Duplicate retrieval and companion/family linkage are distinct from eligibility. KNHANES used only for external validation can qualify; KNHANES merely cited for comparison cannot. S4 illustrates these decisions; it does not replace this rule. |

## Integrated synchronisation principle

v1.2, v1.3 and v1.4 are **data and review-layer versions within this single master**, not competing protocol filenames. This document contains items, choices, branching, units, evidence, JSON keys, the post-hoc purpose/use module and dual-AI/source-based human adjudication procedures. Separate addenda, CSV/TSV/schema/choice-set files are not normative references. Preserve locked P1/P2/final provenance; name new layers only `AI_A_BLINDED`, `AI_B_BLINDED`, `HUMAN_ADJUDICATION`, `FINAL_CONSENSUS`. Historical P1 was migration and P2 was blinded LLM verification; do not retrospectively describe them as two independent AIs or two human reviewers. Do not retrospectively change the 382 locked core responses or existing `KNHANES_studies_v1.2.jsonl`. This integrated protocol governs the outputs.

## 1. Independent-review file rules

- Enter P1 and P2 in their own JSON files.
- Do not expose P1 files or values to P2 before P2 completion.
- Distinguish P1 migration (`migration_validation`) from new source reading (`independent_review`). P2 used only source packages and was a blinded LLM (`P2-CLAUDE-OPUS5`, `reviewer_type=LLM_AGENT`), not a human; do not describe this as independent review by two humans.
- CON present: use CON; no CON and P1=P2: use agreement; P1 differs from P2 without CON: `UNRESOLVED`; P1 alone: `PROVISIONAL`.
- `KHM001_final.json` retains final values, P1/P2 file references, comparisons and CON provenance. Original P1/P2 values remain in locked stage files.

## 3. Units and IDs

- Study `KHM001`; Report `KHM001-R01`; Dataset `KHM001-DS01`; Outcome `KHM001-O01`; Model `KHM001-M01`; Development `KHM001-D01`; Evaluation `KHM001-E01`; Visual `KHM001-V0001`; Supplement `KHM001-S01`.
- Each response has exactly one `primary_unit`; put necessary links in `related_ids`.
- Evaluations link at least `model_id`, `outcome_id`, `dataset_id`. Developments also link model and dataset.

## 4. Evidence and source package

Store evidence once in the same JSON's `evidence_registry`; link each item through `evidence_ids`. Record source file/type, section/subsection, PDF/printed page, object/panel/table coordinates, start/end anchor, excerpt and interpretation status.

Separate source acquisition from review: `availability=ACQUIRED/NOT_ACQUIRED/BLOCKED/NOT_IDENTIFIED`, `review_status=NOT_STARTED/IN_PROGRESS/COMPLETE/NOT_APPLICABLE`, access date, sha256 and notes. Store each supplement in `source_package.supplement_files[]`. Use NR only after reviewing the accessible package; never invent excerpts.

## 5. Response codes

These codes apply only to the locked v1.2 P1/P2/CON layers. Section 18.2 alone defines active dual-AI/human-adjudication statuses, using `UNCLEAR` rather than `UNC`.

- Method use: `USED/NOT_USED/NR/UNC/NA`
- Content: `PRESENT/ABSENT/UNC/NA`
- Reporting completeness: `R/P/NR/UNC/NA`
- Logical judgement: `Y/N/UNC/NA`
- PROBAST+AI: `Y/PY/PN/N/NI/NA`

Do not combine performance, reporting and presence in one Y code. Use `OTHER` consistently and JSON arrays for multiple responses.

## 6. Performance and selected models

The 21 `MET_*_V` value items were removed. Store actual values only in `performance_metrics[]`, by evaluation/model/outcome/dataset/class/threshold/split. Derive `MET_*_R` from those arrays and source-package review. BEST01–03 automatically check `best_model_selections[]` completeness; they are not duplicate manual value entries.

Every `performance_metrics`, `best_model_selections` and `visual_objects` element requires `reviewer_id`, `review_stage`, `status`, `rationale`, `evidence_ids`.

### 6.1 Reason codes for overall classification judgements

Retain `OUT18` and `PRD15` overall grades with unit-level judgements in audit backdata rather than as the principal figure results. The derived final-JSON field `adjudication.classification_reason_codes[]` does not change judgements; it stores `scope`, `unit_id`, `overall_value`, `reason_codes[]`, `rationale`. Permitted reasons follow.

- Outcome: `outcome_rule_not_reconstructable`, `outcome_rule_partly_reconstructable`, `outcome_circularity_or_misalignment`, `outcome_basis_limited`, `insufficient_evidence`, `no_specific_outcome_problem_identified`
- Predictors: `predictor_set_not_reconstructable`, `predictor_set_partly_reconstructable`, `target_component_used_as_predictor`, `near_direct_target_proxy_used`, `post_outcome_predictor`, `predictor_unavailable_at_intended_use`, `target_predictor_misalignment`, `insufficient_evidence`, `no_specific_target_predictor_problem_identified`

## 7. Reporting completeness and other tasks

REP01–19 apply only to D_PROB. Code R when all `required_components` are reported, P when some are reported, and NR when none are reported. Exclude OTHER-task studies from REP assessment; describe their core characteristics and TSK11/NC items without creating a generic reporting score.

## 8. PROBAST+AI

PD/PE wording is an operational summary linked to the official instrument by `official_item_id`. For development: all applicable domains HIGH → HIGH; any LOW → LOW; no LOW but any UNCLEAR → UNCLEAR; all NA → NA. For evaluation: all applicable domains LOW → LOW; any HIGH → HIGH; no HIGH but any UNCLEAR → UNCLEAR; all NA → NA. Preserve locked UNC responses. Development HIGH means high quality (official low quality concern); LOW means low quality (official high quality concern). Evaluation HIGH means high risk of bias: its direction is opposite.

### 8.1 Current reading clarifications (2026-09-24; locked responses unchanged)

The following clarifies the short rule labels for OUT16, PRD13 and PD/PE domain/overall judgements in §15. Do not retrospectively replace historical P1/P2 responses or core records. Item-specific English rules in `tools/protocol_public_english.py` reflect this section in S2.

- OUT16: R2 requires an unambiguous outcome name, ascertainment source/instrument, timing and applicable cutoff/class/composite rules. R1 identifies the outcome but misses a necessary detail (e.g., a scale without its dichotomisation cutoff). R0 cannot recover the actual definition beyond a name. Validity/leakage belong to OUT17/18 and other items; this is not executable-code reproducibility. Use NA only for structural inapplicability, preserving original response-status metadata separately.
- PRD13: R2 requires recoverable candidate and final input sets (including an explicit statement that they coincide), essential definitions/coding and model linkage. R1 means partial recovery (e.g., only a top-10 importance ranking without the candidate list). R0 means neither a usable input set nor its construction can be recovered. A count alone is insufficient. Distinguish this from prediction-time availability, leakage and code reproducibility.
- PD_D1–D4/PE_D1–D4: official Y/PY signalling responses support favourable judgements; N/PN indicate concern, not automatic domain failure. Explain material effects and evidence. NI is insufficient information, not a confirmed defect. Do not interpret the historical §15 phrase `critical-failure rule` as a separate score or automatic rejection algorithm.
- Official locations: Moons et al., BMJ 2025;388:e082505, Supplementary Table 3, Step 3 (development domains 1–4: PDF pp.4,5,6,7; evaluation: pp.9,10,11,12), Step 4 overall judgement p.13. E&E Light is Supplementary Table 4 (development domains: pp.1–2,2–4,5–6,7–8; evaluation: pp.9–10,10–12,12–14,14–16). Article: https://doi.org/10.1136/bmj-2024-082505 ; official downloads: https://www.probast.org/probast_ai/downloads/ . Both attachments were checked against PMC11931409 and retained at `references/guidelines/PROBAST_AI_official_tool_2025.pdf` and `PROBAST_AI_EE_Light_2025.pdf`. Checksums/acquisition sources are in the prompt_079 implementation record.
- Follow the direction-specific domain combinations above and official Step 4. All-NA is this review's applicability convention, not a new official quality category. Record reasons for exceptional overall judgements; do not recode original unit judgements without evidence.

#### M-EXT. Derived evidence-linked model-development audit fields

These fields are derived by fixed rules from values/evidence IDs for `MOD02`--`MOD15`, `BEST02`--`BEST03`, `VI03`, `VI11`--`VI14`, without retrospectively changing the 382 locked source-reading responses. Leave roles unsupported by source evidence `UNCLEAR`. Retain study results in final JSON `adjudication.expanded_model_task_audit` and the relational supplementary dataset.

- `algorithm_family`, `algorithm_name_as_reported`, `algorithm_role`
- `baseline_or_comparator`, `ensemble_status`
- `hyperparameter_tuning_method`, `tuning_data_partition`
- `final_model_selection_metric`, `final_model_selection_dataset`
- `test_set_used_for_selection`, `final_model_fully_specified`
- `software_and_version`, `evidence_location`
- `ml_statistical_relationship`: ML only/no reported link; conventional comparator;
  independent/parallel statistical analysis; ML ranking guided statistical analysis;
  exact variable carryover; unclear relationship

The main questions are (1) whether final-model selection avoided test-data use and (2) whether conventional statistical models served as genuine benchmarks, parallel analyses or downstream inference. Rules are fixed in `tools/build_expanded_model_task_audit.py`.
